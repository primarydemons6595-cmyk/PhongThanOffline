# Bot loot, recovery and skill progression

The previous controller attempted to pick up only the first object immediately beside the bot. Its request left the destination container and slot at zero. It did not navigate to other nearby drops. The combat controller always selected the profession's basic physical skill. Recovery examined only the first inventory page and quick-use slots and recognized ordinary medicine, excluding the native charged life/mana reservoirs.

The replacement controller uses a shared per-map drop index refreshed once per second. Each bot filters actual item/money objects by world, range, ownership/team eligibility and bag capacity. It chooses an accessible inventory slot through `FindBagPosition`, approaches nearby useful loot with the existing bounded route planner and submits `ServerPickUpItem` with that destination. Failed or unreachable objects are temporarily skipped. It respects the ordinary pickup distance and ownership rules; no direct transfer, teleport or item grant is used. Nearby live enemies take precedence over walking to distant loot. Loot activity participates in the normal movement cadence.

Equipment, recovery items, eligible profession books and money can be collected. Auto-equipping evaluates actual `CanEquip` requirements and canonical equipment power and moves owned items through `ServerMoveItem`; it rechecks every 5–10 seconds rather than 20–45 seconds. It does not equip an item whose requirements are unmet. Existing conservative surplus-sale policy remains in place; this change does not introduce selling arbitrary rare equipment.

Recovery covers all inventory pages and quick-use slots. Ordinary medicine uses normal item use. Verified native charged life/mana items use the existing `Reserved=1` auto-dose request instead of repeatedly toggling a reservoir on and off. Consumption logs are emitted only after observing charge/stack removal or a life/mana increase. Health and mana are never granted by the controller.

Owned profession books are used only after the canonical book identity, profession, character level, unlearned status and original `skills.ini` prerequisites permit learning. The usual item-use handler consumes the book and adds the skill. The bot logs a confirmed learn only when both the learned skill and removal of that book identity are observed. Merchant plans may purchase affordable eligible books from actual ordinary-currency stock, through an NPC's offered dialog callback and the normal buy request. No book is created for free. Shop scans and trips are staggered.

Combat selects from actually learned enemy-targeting skills, validates weapon/mount/target rules, audits resource cost and checks cooldown. It favors trainable profession attacks and needed prerequisite skills. Basic attacks remain available when no profession attack is usable. A learned summon can be cast through the normal authoritative summon implementation, respecting resource cost, cooldown and an already living pet. Skill experience still comes from real successful hits and normal engine thresholds, not injected experience or skill points.

Inventory snapshots append learned skill IDs, levels, experience/next thresholds and current mana. These snapshots are observational; log entries named `attack_skill_requested` mean a command was issued, not proof that it hit. Use skill experience changes and actual monster deaths to establish training progress.

Validation: native build succeeds with the existing large-image warning. Existing native book checks pass, 194 original prerequisite checks cover 58 books and 31 prerequisite edges, and cumulative skill-experience/cap checks pass. Live pickup, equipment, consumption and book outcomes must be reported separately from compile/unit-test success.

## Follow-up: resource acquisition and needs priorities

Live drop logs exposed an upstream blocker: normal bot kills reached the official native drop engine but were rejected as `INVALID_REWARD_OWNER` because their connection index is negative. The existing human path still produced items. `PhongThanRewardOwnerAvailable` now admits connected characters or explicitly marked, loaded server bots. Owner/NPC/world checks remain in place. The same predicate is used by the retired fallback drop adapter. No drop table, blue-item probability or player loot rate was changed. The isolated production fallback test now passes 13 checks including loaded bots, unloaded bots and disconnected humans; the shared native predicate is also covered by starter-state tests.

Recovery now looks for an owned potion, then an eligible nearby dropped potion, before deciding to sit. A critically weak bot does not chase a distant potion. Useful rare equipment takes priority over ordinary loot; emergency recovery takes precedence when necessary. Pickup still respects ownership and actual bag capacity.

Equipment with known power zero can fill an empty slot. Both the shared equipment predicate and the candidate-selection comparison now cover that case. Equal-power items do not automatically replace a worn item.

When funds fall below the bot policy reserve (`equipment-policy.ini`, `Policy/MoneyReserve`, default 1000), surplus selection can choose ordinary unneeded equipment without waiting for a full bag or several duplicates. Usable upgrades, unknown-power items, rare/enhanced/set items and locked or scripted items remain protected. Material stacks are not automatically sold because they may be required by quests or crafting. Sales use the actual NPC transaction and confirm item removal plus payment.

An active supported quest takes precedence over shopping and party following. Its required monster remains the training target. Quest accept and reward claims still use real NPC-issued choices. This adapter currently covers Kế Tục; this document does not claim every starter or daily quest has an adapter.

Rare items with an actual profession, sex or series mismatch can be advertised on the trade channel by their current owner. The advertisement uses the real item name, checks ownership and trade locks, and observes existing channel graduation/rate limits plus a 10–20 minute bot cooldown. Future-level upgrades are retained rather than being classified as permanently incompatible. An advertisement does not mean a player trade has been negotiated or completed; that adapter remains separate work.
